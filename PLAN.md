**Основание:** `YORI_TASK.md` (`TASK.md` проекта) от 16 октября 2026 года

## 2. Решения по технологическому стеку

### 2.1. Основной стек

- Next.js 16 App Router на актуальном исправленном стабильном патче.
- React 19, совместимый с выбранным Next.js.
- TypeScript в строгом режиме.
- Tailwind CSS; shadcn/ui точечно, преимущественно для CRM.
- Lucide React для интерфейсных иконок.
- Telegram WebApp API и актуальные совместимые пакеты `@tma.js/sdk`/`@tma.js/sdk-react`.
- grammY для Telegram-бота, работающего через webhook.
- PostgreSQL в Neon.
- Prisma ORM 7, зафиксированный на совместимых стабильных версиях CLI, клиента и Neon-адаптера.
- Zod для проверки всех серверных входных данных.
- React Hook Form для checkout и сложных административных форм.
- Better Auth как основной кандидат для административной авторизации.
- Vitest для unit/integration тестов и Playwright для ключевых пользовательских сценариев и адаптивности.
- Node.js runtime для API, Prisma, авторизации и webhook.

### 2.2. Корректировки исходного предложения

1. **Prisma 7 вместо Prisma 8 на старте.** На дату аудита Prisma 8 отмечена официальной документацией как release candidate. Требование использовать стабильные версии важнее рекомендации Skill по умолчанию. Переход на Prisma 8 можно рассмотреть после GA и проверки функциональности, необходимой YŌRI.
2. **Better Auth вместо Auth.js v5 как предпочтительный вариант.** Auth.js v5 всё ещё документируется как beta, тогда как Better Auth заявляет совместимость с Next.js 16 и Prisma 7. Окончательный выбор подтверждается небольшим техническим прототипом на этапе backend; в любом варианте публичной регистрации не будет.
3. **Next.js устанавливается только после повторной проверки security-релизов.** Следует выбрать актуальный исправленный стабильный патч ветки Next.js 16, а не фиксировать номер, найденный во время аудита, без повторной проверки.
4. **Telegram SDK не является границей доверия.** Клиентская библиотека отвечает за интеграцию интерфейса, но сервер самостоятельно проверяет сырой `initData`, подпись и срок `auth_date`.
5. **Не использовать Edge runtime там, где задействованы Prisma, драйвер БД, хеширование паролей или несовместимые зависимости.** Серверные маршруты проекта ориентируются на Node.js runtime.
6. **Не добавлять Redis, отдельные микросервисы, постоянные workers и платные сервисы в MVP.** Надёжность обеспечивается ограничениями БД, журналами и идемпотентными операциями.

## 3. Целевая архитектура

Проект строится как одно приложение Next.js с несколькими пользовательскими поверхностями и общим сервисным слоем:

```text
Telegram Mini App ─┐
Обычный браузер ───┼──> Next.js App Router
CRM /admin ────────┤      ├─ страницы и layouts
Telegram webhook ──┘      ├─ Route Handlers / Server Actions
                           ├─ сервисный слой
                           ├─ Prisma ──> Neon PostgreSQL
                           └─ Telegram Bot API
```

### 3.1. Слои приложения

1. **Представление**
   - клиентский Mini App layout;
   - отдельный CRM layout;
   - Server Components для первичной выдачи и публичных данных;
   - Client Components только для интерактивности, Telegram API, форм и локальной корзины.

2. **Транспортный слой**
   - Route Handlers для Telegram webhook, Telegram-сессии и публичного API;
   - Server Actions или защищённые admin endpoints для операций CRM;
   - единый формат ошибок без утечки Prisma, Telegram и внутренних деталей.

3. **Сервисный слой**
   - `catalog`: категории, товары, публикация и наличие;
   - `cart-pricing`: проверка позиций и денежные расчёты;
   - `ordering`: создание заказа, идемпотентность, история статуса;
   - `telegram-auth`: проверка `initData`, создание пользовательской сессии;
   - `notifications`: отправка и журналирование Telegram-сообщений;
   - `admin`: права, допустимые изменения и аудит;
   - `settings`: условия доставки и готовность live-режима.

4. **Данные**
   - Prisma отвечает за типизированный доступ и миграции;
   - Neon PostgreSQL хранит пользователей, каталог, заказы, историю, настройки, обработанные updates и журнал уведомлений;
   - все суммы хранятся целыми копейками;
   - Telegram ID хранится как `bigint` с контролируемой сериализацией либо как lossless string; конкретный вариант фиксируется в схеме и API-контрактах.

### 3.2. Предлагаемая структура

## 4. Ключевые потоки

### 4.1. Вход в Mini App

1. Telegram открывает HTTPS URL приложения и передаёт `initData`.
2. Клиент отправляет raw `initData` серверу.
3. Сервер проверяет HMAC-подпись, `auth_date` и структуру данных.
4. После успешной проверки сервер обновляет `TelegramUser` и создаёт защищённую HttpOnly-сессию.
5. Каталог доступен и вне Telegram, но checkout и личные заказы требуют подтверждённой Telegram-сессии.

### 4.2. Создание заказа

1. Клиент передаёт идентификаторы товаров, количество, данные доставки и idempotency key.
2. Сервер проверяет сессию, `ORDER_MODE`, allowlist, Zod-схему и ограничения количества.
3. Сервер повторно получает цены, публикацию и наличие из БД.
4. Сервер рассчитывает подытог, доставку, скидку и итог в копейках.
5. В одной транзакции создаются заказ, снимки позиций и начальная запись истории статуса.
6. Уникальное ограничение на idempotency key предотвращает дубликат при повторном запросе.
7. Попытка уведомления записывается в `NotificationLog`; ошибка Telegram не отменяет заказ.
8. CRM показывает состояние уведомления и позволяет выполнить ограниченный ручной повтор.

### 4.3. Обработка Telegram webhook

1. Route Handler ограничивает метод и размер тела.
2. Проверяется `X-Telegram-Bot-Api-Secret-Token` постоянным по времени сравнением.
3. В БД регистрируется `update_id` с уникальным ограничением.
4. Уже обработанный update завершается успешным ответом без повторного эффекта.
5. Поддерживаются `/start`, `/help`, `/orders` и необходимые callback-сценарии.
6. Handler отвечает быстро; долговечное состояние хранится в БД.

### 4.4. Работа CRM

1. Публичной регистрации нет; первый администратор создаётся отдельной серверной командой из env.
2. Пароль хранится как адаптивный хеш; сессия использует Secure/HttpOnly/SameSite cookies.
3. Proxy может выполнять ранний redirect, но каждый Route Handler и Server Action заново проверяет сессию и роль.
4. Изменение заказа проходит через таблицу допустимых переходов статусов и создаёт audit-запись.
5. Изменение каталога инвалидирует или обновляет публичный кэш.

## 5. Ограничения Vercel Hobby и Neon

### 5.1. Vercel Hobby

- Использовать только для личной некоммерческой разработки и закрытого тестирования.
- Реальные коммерческие заказы требуют Vercel Pro/Enterprise либо другого хостинга, допускающего коммерческую эксплуатацию.
- До смены режима приложение работает с `ORDER_MODE=private_test`; checkout разрешён только allowlist Telegram ID.
- Live-режим нельзя включить обычным переключателем в CRM. Требуется серверная проверка готовности: разрешающий коммерцию хостинг, действующий оператор, зоны, условия доставки, платежные варианты и достоверные контакты.
- Бот работает только через webhook. Постоянный Node-процесс и production long polling не используются.
- Приложение не зависит от Vercel Cron: Hobby допускает не чаще одного запуска в сутки и не гарантирует точное время.
- Надёжность уведомлений строится на записях в БД и ручном повторе, а не на локальных таймерах функции.
- Не сохранять uploads в файловой системе Functions. В MVP используются подготовленные локальные assets в `public/`.
- Тело запроса и ответа функции должно оставаться значительно ниже лимита платформы; webhook получает отдельный строгий лимит.
- Продолжительность функций зависит от режима Fluid Compute. Все пользовательские запросы проектируются короткими и не опираются на максимальный timeout.
- Следить за Function Invocations, CPU, памятью, Image Optimization и размерами deployment/function bundle.

### 5.2. Neon PostgreSQL

- Runtime использует pooled URL; миграции — direct URL, если этого требует выбранная конфигурация Prisma 7.
- `DATABASE_URL` и `DIRECT_URL` не попадают в клиентский bundle и репозиторий.
- Prisma Client переиспользуется корректно для Next.js development/serverless lifecycle.
- Миграции запускаются отдельно от пользовательских запросов; `prisma migrate dev` не выполняется в production runtime.
- Регион Vercel выбирается близко к Neon.
- Учитывать cold start/scale-to-zero, квоты compute и storage.
- Seed содержит только вымышленные тестовые данные и не содержит реальных персональных данных.
- Preview deployment не должен случайно изменять production-базу; при возможности применять отдельную Neon branch или отдельный env.

## 7. Подробный план этапа 1: дизайн и клиентский интерфейс

### 7.1. Подготовка проекта

- повторно проверить актуальные стабильные версии и security advisories;
- инициализировать Next.js App Router с TypeScript strict, Tailwind и ESLint;
- определить scripts для `dev`, `lint`, `typecheck`, `test`, `build`;
- настроить базовые layouts для Mini App и будущей CRM;
- не подключать Neon, Telegram webhook и production auth на этом этапе;
- завести типизированные данные-заготовки, максимально близкие к будущей модели БД.

### 7.2. Визуальная концепция YŌRI

Сначала подготовить и критически проверить компактную дизайн-концепцию:

- палитра из 4–6 именованных цветов на базе глубокого угольного, тёплого молочного и томатно-красного;
- отдельные семантические токены для поверхности, текста, границ, акцента, успеха, предупреждения и ошибки;
- светлая и тёмная темы с контрастом WCAG;
- одна или две осознанно выбранные гарнитуры с полноценной кириллицей;
- шкала размеров текста, расстояний, радиусов и теней;
- правила фото: единый свет, ракурс, фон, насыщенность и кадрирование;
- правила карточек товара, бейджей, кнопок количества и нижней навигации;
- один выразительный приём бренда, основанный на еде и композиции, без перегрузки декоративной «японской» символикой;
- motion только для понятного отклика на действие, с поддержкой reduced motion.

До написания экранов концепция проверяется на признаки шаблонного решения: одинаковые карточки для любой иерархии, случайные градиенты, декоративные labels, избыток теней и анимаций. Необоснованные элементы удаляются или заменяются.

### 7.3. Контент и изображения

- составить стартовый набор минимум из 24–25 позиций по категориям ТЗ;
- проверить непротиворечивость названия, состава, веса, количества штук и фотографии;
- подобрать реальные фотографии из источников с разрешённым использованием;
- исключить чужой ресторанный брендинг и неподходящие изображения;
- сохранить оригинальный URL, автора и основание использования для будущего `ASSET_SOURCES.md`;
- преобразовать изображения в оптимизированные WebP/AVIF и хранить локально;
- подготовить содержательные alt-тексты;
- ограничить исходные размеры и количество вариантов с учётом квот Vercel Image Optimization.

### 7.4. Экран «Главная»

- логотип/словесный знак YŌRI;
- выразительный первый экран с релевантной фотографией еды и переходом в каталог;
- горизонтальный список категорий;
- блоки «Популярное» и «Советуем попробовать» как ручные флаги данных;
- поиск по названию;
- нижняя навигация из пяти пунктов;
- состояние «Приём заказов сейчас закрыт» без технических объяснений для посетителя;
- skeleton, empty и error состояния.

### 7.5. Экран «Каталог»

- липкий поиск и доступный переключатель категорий;
- сортировка по цене и ручному порядку;
- карточки с фото, названием, составом, весом/количеством, ценой и допустимым бейджем;
- работающая кнопка быстрого добавления;
- видимое состояние недоступного товара;
- сохранение позиции прокрутки при возврате из карточки товара;
- оптимизация длинного списка и изображений.

### 7.6. Экран товара

- крупное соответствующее блюду фото;
- название, состав, аллергены, вес, количество штук и цена;
- выбор количества в допустимом диапазоне;
- работающая кнопка добавления в корзину;
- Telegram Back Button с feature detection и браузерный fallback;
- понятное состояние отсутствия товара.

### 7.7. Экран корзины

- позиции с миниатюрами и ценами;
- изменение количества, удаление и очистка;
- расчёт подытога, доставки и итоговой суммы в целых копейках;
- локальное сохранение с версией схемы данных;
- корректное восстановление после перезапуска;
- состояние пустой корзины;
- визуальная подготовка к будущему сообщению об изменении цены/наличия;
- кнопка перехода к checkout, которая на первом этапе ведёт в явно подготовленный интерфейс без создания серверного заказа.

### 7.8. Telegram и адаптивность

- использовать CSS variables для Telegram theme params;
- учитывать `safeAreaInset`, `contentSafeAreaInset` и нижнюю навигацию;
- проверять поведение при появлении экранной клавиатуры;
- обеспечивать touch targets не менее комфортного мобильного размера;
- не делать Telegram API обязательным для каталога в обычном браузере;
- применять haptic feedback только при поддержке;
- не доверять `initDataUnsafe` для авторизации.

### 7.9. Визуальная проверка и приёмка

Целевой сценарий проверки:

```text
Главная → поиск/категория → каталог → товар → добавление → корзина → изменение количества
```

Проверки:

- viewport 320, 375, 390, 430 и 768 px; дополнительно обзор 1024 и 1440 px;
- светлая и тёмная темы;
- отсутствие горизонтального скролла и обрезки текста;
- нижняя навигация не перекрывает контент;
- фото не прыгают при загрузке и имеют корректное соотношение сторон;
- все основные действия изменяют интерфейс;
- нет framework overlay и критических ошибок консоли;
- доступны focus states, имена controls и reduced motion;
- скриншоты ключевых экранов для согласования.

**Контрольная точка этапа 1:** представить концепцию, работающие экраны и результаты визуальной проверки. Не переходить к checkout/backend до явного одобрения дизайна.

## 8. Стратегия тестирования

### Unit

- денежная арифметика и доставка;
- нормализация телефона;
- допустимые переходы статусов;
- правила private/live mode;
- построение Telegram data-check-string и проверка срока данных;
- сериализация Telegram ID.

### Integration

- сервер пересчитывает подменённые цены;
- заказ и позиции создаются атомарно;
- один idempotency key создаёт один заказ;
- пользователь читает только собственные заказы;
- неверный webhook secret отклоняется;
- повторный `update_id` не обрабатывается повторно;
- сбой уведомления сохраняется, заказ остаётся;
- неавторизованная admin-операция отклоняется;
- изменение товара через CRM отражается в каталоге.

### E2E

- каталог, поиск, фильтрация и карточка товара;
- корзина, восстановление и checkout allowlisted-пользователя;
- заказ появляется в CRM;
- менеджер меняет статус;
- клиент видит новый статус;
- Telegram API мокается в CI;
- основные responsive viewports и браузерный просмотр вне Telegram.

## 9. Основные риски и меры

| Риск | Мера |
|---|---|
| Коммерческая эксплуатация на Hobby | Жёсткий private mode, документация и серверный readiness gate для live |
| Изменение API Prisma 8 | Начать со стабильной Prisma 7, обновляться отдельным решением |
| Beta-статус Auth.js v5 | Предпочесть Better Auth после короткой проверки интеграции |
| Повторные checkout/webhook | Уникальные ключи и транзакции БД |
| Ошибка Telegram после создания заказа | `NotificationLog`, независимое сохранение заказа, ручной retry |
| Cold start Neon | Pooled connection, близкий регион, короткие запросы и понятные loading states |
| Утечка персональных данных через кэш/логи | Dynamic/private responses, маскирование, безопасные логи |
| Устаревшая цена в корзине | Обязательный серверный пересчёт и подтверждение изменений |
| Недоступные или нелицензированные фото | Локальные assets, журнал источников, ручная проверка соответствия |
| Фиктивные обещания сервиса | Редактируемые фактические данные и закрытый приём заказов по умолчанию |
| Недоступность Browser-инструмента | Повторная проверка перед QA, затем Playwright по правилам Skill |
