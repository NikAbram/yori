# YŌRI — Telegram Mini App + бот + панель управления заказами

**Техническое задание для Codex**  
**Этот файл является `TASK.md` проекта; отдельный дублирующий `TASK.md` не требуется.**  
**Дата:** 16 октября 2026 г.  
**Тип приложения:** Telegram Mini App для доставки роллов и суши, Telegram-бот, backend и собственная админ-панель.  
**Основной язык интерфейса:** русский. **Валюта:** российский рубль (₽).  
**Целевой хостинг разработки:** Vercel Hobby + внешний PostgreSQL (Neon Free).

> Важно: Vercel Hobby допускает только личное некоммерческое использование. Разработка и личное некоммерческое тестирование допустимы в рамках условий провайдера, но публичное использование для коммерческого портфолио, продвижения фриланс-услуг или приёма реальных заказов необходимо размещать на тарифе/хостинге, разрешающем коммерческую деятельность. Не обходить ограничения провайдера.

## 1. Цель и ожидаемый результат

Разработать визуально законченный, технически полноценный сервис **YŌRI — доставка суши и роллов** с общим backend для Telegram Mini App, Telegram-бота и CRM/админ-панели.

Функциональность:
- пользователь открывает бота и запускает Mini App;
- изучает каталог, карточки блюд, состав, фотографии, вес и цены;
- кладёт товары в корзину, меняет количество, оформляет заказ в разрешённом режиме;
- видит историю и статус собственных заказов;
- менеджер получает уведомление о заказе в Telegram;
- менеджер через админ-панель редактирует каталог и обрабатывает заказы;
- изменение статуса отражается у клиента и при разрешённых Telegram-сообщениях вызывает уведомление.

Нужен работающий продукт, а не только макеты. Не оставлять фиктивные кнопки, мёртвые формы и пустые страницы.

### 1.1. Внешний вид и добросовестность

Публичный интерфейс должен выглядеть как полноценное ресторанное приложение: **не выводить слова «демонстрационный проект», «проект для портфолио», «тестовый сайт», «учебный проект» и аналогичные надписи на видимых клиентских страницах**. Внутренние файлы разработки могут обозначать тестовые данные и тестовый режим.

При этом:
- не выдавать вымышленные отзывы, рейтинги, награды, юридическое лицо, адрес ресторана, телефон, часы обслуживания и обещания доставки за подтверждённые факты;
- не использовать чужие логотипы и фотографии товаров других ресторанов без прав;
- не принимать реальные клиентские заказы, пока нет действующего ресторана, персонала и готовности исполнить заказ;
- до такого подключения использовать `ORDER_MODE=private_test` и ограничить оформление allowlist Telegram ID, при этом каталог и визуальный интерфейс остаются доступны для просмотра;
- публичным пользователям вне allowlist показывать обычное состояние сервиса «Приём заказов сейчас закрыт», без указаний на портфолио;
- для будущего `ORDER_MODE=live` предусмотреть переключение только после осознанной настройки операционных данных и выбора хостинга, разрешающего коммерческое использование.

## 2. Технологический стек

- **Next.js App Router**, React, TypeScript strict — единое приложение для Mini App, API и админ-панели.
- **Tailwind CSS**, shadcn/ui по необходимости (главным образом для админки), Lucide React.
- **Telegram Mini Apps SDK** (актуальная совместимая версия официального SDK/пакетов экосистемы TMA) и Telegram WebApp API.
- **grammY** или эквивалентная поддерживаемая библиотека Bot API — обработка webhook через Next.js Route Handler.
- **PostgreSQL** в Neon; **Prisma ORM** и миграции.
- **Zod** — валидация всех серверных входных данных; React Hook Form для формы заказа.
- **Auth.js** либо эквивалентная защищённая серверная сессия для администратора с учётом поддержки актуального Next.js.
- **Vitest** — unit/integration тесты; **Playwright** — e2e и проверка адаптивности.
- Node.js runtime для API и Prisma, не Edge runtime при несовместимости драйвера.

Устанавливать актуальные стабильные совместимые версии; внимательно следовать реальным версиям Prisma/Next.js, не копировать устаревшие конфигурации. Избегать отдельных микросервисов, Redis, постоянных background workers и платных зависимостей в MVP.

## 3. Дизайн и пользовательский опыт

### 3.1. Бренд

**Название:** YŌRI. **Категория:** суши и роллы с доставкой.  
**Визуальный характер:** современный японский фуд-бренд, премиальный, аппетитный, динамичный, но не перегруженный.

Предлагаемое направление: глубокий угольный, тёплый молочный, томатно-красный акцент; Codex должен создать полноценную визуальную концепцию и систему дизайн-токенов, а не механически использовать случайные цвета. Крупные фото блюд, аккуратные бейджи, сильная типографика с кириллицей и осмысленные микроанимации.

Требования:
- mobile-first (320–430 px в первую очередь); также 768, 1024 и 1440 px;
- нативное ощущение внутри Telegram, плавные переходы, доступные размеры тач-целей;
- учитывать Telegram safe area/content safe area, нижнюю панель, экранную клавиатуру;
- светлая и тёмная темы с корректным контрастом; предпочтение Telegram theme params;
- поддерживать Telegram Back Button, haptic feedback как необязательное улучшение с feature detection;
- анимации с учётом `prefers-reduced-motion`;
- явные состояния loading, empty, error, retry, unavailable;
- админ-панель — удобная на десктопе и рабочая на мобильных;
- не использовать автоматические фальшивые отзывы, рейтинг 4.9 без источника, счётчики «10 000 заказов» и фиктивные скидки.

### 3.2. Фотографии блюд

Изображения должны быть **реальными фотографиями еды**, а не нерелевантными заглушками или случайными изображениями одного блюда для всех карточек.

- Подобрать визуально единый набор фотографий роллов, сетов, суши, супов, закусок и напитков из источников с разрешённым использованием (например, Pexels/Unsplash с проверкой условий на дату скачивания) либо собственных/licensed assets.
- Для каждого товара фото должно соответствовать заявленному типу блюда; не использовать чужие брендированные снимки или защищённые логотипы ресторанов.
- Сохранить изображения локально в `/public/images/products` в оптимизированном WebP/AVIF, снабдить alt-текстами.
- Зафиксировать источник и лицензию/основание использования в `ASSET_SOURCES.md` (это внутренний файл; не выводить в клиентском интерфейсе).
- Исключить битые картинки, случайные несоответствия и permanent hotlinking к нестабильным URL. Если надлежащего фото нет, подобрать другое легальное фото, не изображать будто нужное блюдо присутствует на неподходящем снимке.
- Разумно сжимать изображения для лимитов Vercel Hobby.

## 4. Telegram-бот

Создать бота через @BotFather, но **не генерировать и не фиксировать секретный BOT_TOKEN в исходном коде**; предоставить пользователю отдельную инструкцию настройки.

Поддерживаемые команды:
- `/start`: короткое приветствие, кнопка `🍣 Открыть меню` (web_app), кнопка `Мои заказы`.
- `/help`: помощь и порядок оформления.
- `/orders`: переход в Mini App на историю заказов (при доступном корректном механизме deep link/startapp).

Дополнительно:
- зарегистрировать Menu Button в BotFather / API для запуска приложения;
- webhook `POST /api/telegram/webhook` через Next.js Route Handler;
- валидировать заголовок `X-Telegram-Bot-Api-Secret-Token` и ограничивать размер тела запроса;
- дедуплицировать Telegram update по `update_id` в БД;
- отправлять менеджеру уведомления о новых заказах с безопасным номером заказа, составом, суммой и статусом;
- отправлять клиенту сообщения о подтверждении и смене статуса **только когда бот имеет право ему писать**; не считать доставку уведомления гарантированной;
- сохранять статус доставки уведомлений/ошибку и предусмотреть ручную повторную отправку из админки;
- отвечать на webhook своевременно, обрабатывать возможные повторные запросы;
- не использовать `getUpdates` long polling в production.

## 5. Telegram Mini App: клиентские экраны

### 5.1. Главная `/`
- Логотип YŌRI, фирменный баннер, кнопка открытия каталога.
- Категории: Сеты, Классические роллы, Запечённые роллы, Темпура, Суши, Супы и закуски, Напитки.
- Блоки «Популярное» и «Советуем попробовать» на основании флага в БД, а не фальшивых статистик.
- Нижняя навигация: Главная, Каталог, Корзина, Заказы, Профиль.
- Поиск по названиям товаров, быстрый переход в карточку.

### 5.2. Каталог `/catalog`
- Карусель/переключатель категорий и карточки продуктов.
- У каждой карточки: фото, название, вес/количество, краткий состав, текущая цена в ₽, бейдж (только если задан администратором), кнопка `+`.
- Фильтр по категории; поиск; сортировка по цене и популярности (последняя только при наличии фактических данных или ручного порядка).
- Наличие товара контролируется БД, недоступный товар нельзя заказать.

### 5.3. Карточка товара `/product/[slug]`
- Крупное фото, имя, цена, состав, вес, количество кусочков, сведения об основных аллергенах при их наличии.
- Изменение количества, кнопка `Добавить в корзину`.
- Никаких неработающих модификаторов и обязательных опций без backend-поддержки.

### 5.4. Корзина `/cart`
- Список товаров с миниатюрами; изменение количества; удаление; очистка корзины.
- Подытог, стоимость доставки, скидка (если реально рассчитана), итог.
- Локальное сохранение корзины с восстановлением после перезапуска Mini App; синхронизация с серверными ценами перед оформлением.
- Сообщения об изменении цены или отсутствии товара; подтверждение пользователем обновлённой суммы.
- Избегать двойной отправки/заказа при повторном клике.

### 5.5. Оформление `/checkout`
Поля:
- имя получателя (обязательно);
- телефон (обязательно, нормализация + валидация);
- город и адрес доставки (город задаётся активной зоной обслуживания при настоящем запуске); улица, дом, квартира/офис, подъезд, этаж, комментарий;
- удобное время: `Как можно скорее` (для MVP), без обещания конкретного ETA;
- способ оплаты: `При получении` (наличные/карта у курьера только при реально доступной опции), онлайн-оплату не реализовывать;
- чекбокс согласия на обработку персональных данных;
- итоговый состав заказа, подытог, доставка и сумма к оплате.

Правила:
- сумма вычисляется заново на сервере по действующим ценам в БД;
- минимальная сумма заказа и доставка задаются в настройках (стартовые ориентиры 700 ₽, доставка 199 ₽, бесплатно от 1 800 ₽);
- оплата и доставка доступны только когда они реально включены администратором; не обещать недоступных услуг;
- заказ сохраняется атомарно, каждая позиция хранит snapshot названия, цены, количества;
- повторная отправка того же checkout idempotency key не создаёт дубликат;
- приватный тестовый режим: оформлять заказы могут только Telegram ID из allowlist; заказ помечается тестовым **только внутри БД и админки** и не попадает реальным операторам/клиентам;
- публичный посетитель не должен иметь возможность незаметно создать заказ, который некому исполнить.

### 5.6. Заказы `/orders` и `/orders/[id]`
- История заказов текущего верифицированного Telegram пользователя.
- Детали: номер, товары, итог, дата, адрес (маскировать в логах), способ оплаты и текущий статус.
- Статусы: `Новый`, `Подтверждён`, `Готовится`, `Передан курьеру`, `Доставлен`, `Отменён`.
- При необходимости показывать таймлайн; не обещать отслеживание GPS без интеграции.

### 5.7. Профиль `/profile`, справочные страницы
- Данные пользователя Telegram: имя и username, только после безопасной проверки `initData`.
- Сохранение телефона и адресов при явном согласии (добавление/удаление).
- Информация о составе, контактах, условиях доставки и политике данных должна быть редактируема администратором, а не содержать вымышленные юридические реквизиты.
- Ссылка на помощь через Telegram-бота.

### 5.8. Поведение вне Telegram
- Каталог и корзина должны открываться в обычном браузере для QA и визуального просмотра.
- Там, где требуется Telegram-авторизация, предложить открыть приложение в Telegram.
- В production НЕ использовать небезопасный dev-bypass и не разрешать создание заказов без серверной аутентификации.

## 6. CRM и административная панель `/admin`

Админ-панель открывается отдельно от клиентского Mini App, имеет собственный layout и защищённый вход `/admin/login`.

### 6.1. Авторизация
- Без публичной регистрации. Один исходный администратор создаётся отдельной серверной командой/seed из env, пароль хранится только как Argon2id или другой надёжный адаптивный хеш.
- Защищённая серверная сессия, secure/HttpOnly cookies, ограничение попыток входа, CSRF в зависимости от выбранного auth-решения.
- Все админ-операции требуют серверной проверки прав. Нельзя полагаться только на middleware или скрытые кнопки.

### 6.2. Dashboard
- Число заказов за выбранный период, новые заказы, выручка по заказам со статусом `Доставлен` (только реальные, не тестовые), список последних заказов.
- Не создавать фальшивые метрики, показывать реальные расчёты из БД.

### 6.3. Управление заказами
- Таблица: номер, дата, клиент, телефон, позиции, сумма, способ доставки, статус.
- Поиск по номеру/телефону, фильтры по статусу и дате; серверная пагинация.
- Детальный просмотр заказа; изменение статуса; заметка менеджера; подтверждение потенциально необратимых действий.
- Аудит изменений статусов (кто, когда, старое/новое значение).
- Статусы меняются в соответствии с допустимыми переходами; доставленный заказ нельзя бесследно изменить на новый.
- Повторная отправка Telegram-уведомления при ошибке, без бесконечных автоматических повторов.

### 6.4. Управление каталогом
- CRUD категорий и товаров.
- Название, slug, состав, аллергены, вес, число штук, фото, цена, бейдж, порядок, `isAvailable`, `isPublished`.
- Поддержка установки URL/пути к заранее подготовленным локальным изображениям; **загрузка файлов в файловую систему Vercel Functions запрещена**.
- Валидация цен, уникальности slug, корректности фото; редактирование отображается в клиентском интерфейсе.

### 6.5. Настройки
- Название/описание бренда, правила доставки, минимум заказа, стоимость доставки, порог бесплатной доставки.
- Доступность заказов и способа оплаты; режим `private_test`/`live` определяется защищённой инфраструктурной настройкой, которую нельзя перевести в live случайным нажатием обычной кнопки.
- Telegram chat ID менеджеров, тексты уведомлений при необходимости, контактные данные, ссылки на правовые документы — только достоверные сведения.

## 7. База данных и модели Prisma

Ввести следующие сущности (поля уточнить с типами, индексами и отношениями):

- `TelegramUser`: id, `telegramId` (уникальный bigint или lossless string), firstName, username, createdAt, updatedAt, lastSeenAt.
- `AdminUser`: id, email unique, passwordHash, role, createdAt.
- `Category`: id, name, slug unique, sortOrder, isPublished.
- `Product`: id, categoryId, name, slug unique, description, ingredients, allergens, imagePath, weightGrams, piecesCount nullable, `priceKopeks` integer, isAvailable, isPublished, isFeatured, sortOrder, createdAt, updatedAt.
- `Order`: id, readable orderNo unique, userId, recipientName, phone, address fields, customerNote, `subtotalKopeks`, `deliveryKopeks`, `discountKopeks`, `totalKopeks`, paymentMethod, status, `isTest`, `idempotencyKey` unique, consentAcceptedAt, createdAt, updatedAt.
- `OrderItem`: id, orderId, productId nullable, productNameSnapshot, unitPriceKopeks, quantity, lineTotalKopeks.
- `OrderStatusHistory`: id, orderId, fromStatus, toStatus, changedBy, note, createdAt.
- `ProcessedTelegramUpdate`: updateId unique, createdAt.
- `NotificationLog`: id, orderId nullable, recipientType, telegramChatId, eventType, status, attemptCount, errorText sanitized, createdAt, updatedAt.
- `CustomerAddress` (optional if included in MVP): userId, label, normalized fields, createdAt.
- `SiteSettings`: singleton with delivery parameters, contact/display info and timestamps.

Все денежные значения хранятся **в копейках целыми числами**, арифметика выполняется без float. Уточнить безопасные типы и сериализацию Prisma bigint и целочисленных сумм. Изменения schema — только через миграции, с воспроизводимым seed.

## 9. Серверная архитектура и API

Один Next.js-проект:
- `POST /api/telegram/webhook` — обработка Telegram update.
- `POST /api/auth/telegram` — проверка raw initData и создание защищённой сессии Mini App; либо безопасное session middleware согласно SDK.
- `GET /api/catalog` и `GET /api/products/[slug]` — каталог и товар (или эквивалент через безопасные Server Components).
- `POST /api/orders` — оформить заказ с Zod + Telegram-auth + idempotency + пересчёт сумм.
- `GET /api/orders` и `GET /api/orders/[id]` — только заказы текущего пользователя.
- `GET/POST/PATCH/DELETE /api/admin/...` и/или Server Actions — только с серверной авторизацией администратора.

Не создавать ненужный дублирующий API, если Server Actions достаточно, но сохранить ясную границу полномочий. Рекомендуется сервисный слой `catalog`, `ordering`, `notifications`, `telegram-auth`, `admin` независимо от транспортного слоя.

### 9.1. Безопасность
- Валидировать Telegram `initData` по серверному HMAC SHA-256 алгоритму из официальной документации, сравнивать подписи в постоянном времени и проверять `auth_date`; не доверять `initDataUnsafe`.
- Не принимать `telegramId` от клиента как доказательство авторизации.
- Для webhook проверять `secret_token`, удалять из логов секреты и персональные данные, применять dedup `update_id`.
- Установить лимиты количества, размера payload, rate limiting checkout/login, Zod validation и допустимые переходы статусов.
- Проверять права на заказ на сервере; запретить чтение чужих заказов по ID.
- Ограничить CORS и origin там, где применимо, использовать безопасные cookies, HTTPS и noindex для админки.
- Скрывать ошибки Prisma/Telegram от пользователя, логировать обобщённые безопасные сведения.
- Не хранить BOT_TOKEN и DATABASE_URL в клиентском bundle/репозитории.

### 9.2. Надёжность заказов
- Создавать заказ и его позиции транзакционно.
- Цена, доступность, итог, минимальная сумма и доставка проверяются на сервере непосредственно перед записью.
- Сохранять snapshot на момент заказа.
- Уведомление менеджеру не должно блокировать сохранение заказа: ошибки Telegram отражаются в NotificationLog, возможна безопасная повторная отправка.
- Повторные update/checkout не должны порождать дубликаты.

## 10. Ограничения Vercel Hobby и Neon

### 10.1. Vercel
- Mini App, админка, API и webhook развернуть как один Next.js-проект на Vercel.
- Только **webhook**, никакого постоянного Node-процесса, бесконечного polling, локальных фоновых очередей или ожидания между запросами.
- Внутренние интервалы/таймеры не считать надёжными фоновых задачами.
- Для коротких побочных задач можно использовать поддерживаемое `after()`/`waitUntil()` с учётом лимитов функции, но надёжные уведомления вести через запись в БД.
- Не использовать частые Vercel Cron: на Hobby — не чаще раза в сутки; приложение не должно от них зависеть.
- Не загружать медиа на диск функций: файловая система эфемерна/не подходит для постоянных загруженных файлов.
- Фото продуктов подготовить заранее и положить в `public/`; редактор админки в MVP выбирает локальный asset/путь, а не сохраняет upload в Vercel FS.
- Проверять usage-лимиты, размер функции, совместимость Node runtime, регион размещения относительно БД, количество запросов к Prisma.
- Указать ограничения коммерческого использования Hobby в `DEPLOY.md`, не скрывать.

### 10.2. Neon PostgreSQL
- Бесплатная внешняя база данных с лимитами Free; не считать её частью бесплатной квоты Vercel.
- Использовать подходящее pooled соединение для runtime и direct connection для миграций, если версия Prisma/драйвер требует разделения.
- Настроить миграции отдельно от пользовательского runtime; не выполнять `prisma migrate dev` при production-запросах.
- Не сохранять реальные клиентские данные в seed.

## 13. Тестирование

Обязательные тесты:

1. Каталог загружается с корректными карточками и фотографиями; фильтрация/поиск работает.
2. Добавление, удаление, изменение количества и восстановление корзины работает.
3. Корзина корректно пересчитывает итог без ошибок округления.
4. Невалидный Telegram initData, просроченный auth_date и подмена Telegram ID отклоняются.
5. Без Telegram-сессии нельзя читать чужие заказы или оформить заказ.
6. Суммы/товары в клиентском запросе нельзя подделать: сервер пересчитывает по БД.
7. Двойной клик или повтор запроса с тем же idempotency key создаёт один заказ.
8. Повторный webhook update не обрабатывается дважды; неверный secret token даёт отказ.
9. Ошибка отправки уведомления не удаляет заказ; админ видит статус уведомления.
10. Неавторизованный пользователь не может читать/менять админские данные.
11. Редактирование товара/наличия/цены через CRM изменяет Mini App.
12. Переход заказа между статусами записывается в историю и отображается клиенту.
13. Без allowlist в `private_test` создание заказов заблокировано.
14. Проверка Telegram Android/iOS/Web по возможности, плюс обычный браузер; mobile viewports 320, 375, 390, 430, 768 и desktop 1440.
15. Не должно быть горизонтального скролла, перекрытия Telegram safe area, пустых картинок, критических консольных ошибок.
16. `lint`, `typecheck`, `test`, `build` успешны; реально запускать проверки и честно отчитываться.

По возможности добавить Playwright e2e для сквозного теста: заказ от allowlisted Telegram-пользователя → запись в БД → уведомление менеджеру (Telegram API мокается в CI) → изменение статуса в админке → просмотр статуса клиентом.
