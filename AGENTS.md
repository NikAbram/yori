# AGENTS.md — правила работы с проектом YŌRI

Этот файл содержит постоянные инструкции для AI-агентов и разработчиков, изменяющих репозиторий YŌRI.

## 1. Источники требований

Перед любой реализацией обязательно полностью прочитать:

1. `AGENTS.md` — правила работы с репозиторием;
2. `YORI_TASK.md` — `TASK.md` проекта, основное техническое задание;
3. `PLAN.md` — согласованный подход, архитектура и этапы;
4. `PROGRESS.md` — текущий статус выполнения, технической проверки и пользовательского согласования этапов.

`YORI_TASK.md` является файлом `TASK.md` этого проекта. Отдельный дублирующий `TASK.md` не требуется. Во всех инструкциях и ссылках упоминание `TASK.md` означает `YORI_TASK.md`.

Перед началом разработки обязательно ознакомиться с `PROGRESS.md`, определить по нему текущую согласованную часть и сверить статус с `PLAN.md` и фактическим состоянием репозитория. Не повторять уже подтверждённую работу и не переходить к следующей части или этапу без предусмотренного согласования. После завершения и проверки части или этапа обновлять `PROGRESS.md` фактическими результатами.

При конфликте инструкций применять следующий приоритет:

1. последнее явное указание пользователя;
2. `YORI_TASK.md`;
3. утверждённый `PLAN.md`;
4. этот `AGENTS.md`;
5. общие рекомендации Skills и библиотек.

Не менять требования и не расширять область проекта без явной необходимости. Если решение в `PLAN.md` устарело из-за новой стабильной версии или официальной документации, сначала привести доказательства и согласовать существенное изменение.

## 2. Этапность и согласование

Работать по этапам из `PLAN.md`:

0. аудит требований;
1. визуальная концепция и клиентская основа;
2. полный клиентский интерфейс;
3. backend, Neon и Prisma;
4. Telegram-бот;
5. CRM;
6. QA, безопасность и размещение.

Правила этапов:

- не переходить к следующему крупному этапу без явного согласования пользователя;
- после этапа 1 обязательно остановиться для отдельного согласования дизайна;
- в рамках текущего согласованного этапа самостоятельно выполнять все необходимые подзадачи;
- перед существенным отклонением от `PLAN.md` объяснить причину и влияние;
- не считать этап законченным, пока его результат не проверен в объёме, указанном в `PLAN.md` и `YORI_TASK.md`.

После каждого крупного этапа сообщать:

- что реализовано;
- какие файлы изменены;
- какие команды и тесты фактически выполнены;
- какие ограничения и непроверенные сценарии остались;
- какой этап предлагается следующим.

| Skill | Когда применять |

| `vercel-react-best-practices` | Создание и проверка React/Next.js компонентов, data fetching, bundle и производительность |

Не запускать установку, синхронизацию или генераторы Skill без необходимости текущего согласованного этапа.

## 4. Зафиксированный стек

- Next.js App Router на актуальном исправленном стабильном патче ветки 16.
- React и React DOM совместимых стабильных версий.
- TypeScript strict.
- Tailwind CSS.
- shadcn/ui точечно, прежде всего для CRM; не превращать клиентский интерфейс в стандартный набор shadcn-карточек.
- Lucide React для интерфейсных иконок.
- `@tma.js/sdk` и `@tma.js/sdk-react` для клиентской интеграции Telegram Mini Apps.
- Telegram WebApp API как источник поддерживаемых возможностей клиента.
- grammY с webhook; production long polling запрещён.
- PostgreSQL в Neon.
- Prisma ORM 7 со стабильными совместимыми версиями CLI, клиента и адаптера.
- Zod для всех серверных входных данных.
- React Hook Form для сложных форм.
- Better Auth как предпочтительный вариант административной авторизации после проверки совместимости.
- Vitest и Playwright.
- Node.js runtime для Prisma, auth, API и Telegram webhook.

Не переходить на Prisma 8, пока она не стала стабильной и переход отдельно не обоснован. Не выбирать beta- или canary-версии основных зависимостей без подтверждённой необходимости.

Перед первой установкой и перед крупным обновлением:

- проверить актуальные стабильные версии и официальные security advisories;
- убедиться в совместимости Node.js, Next.js, React, Prisma, адаптера Neon и auth-библиотеки;
- фиксировать версии lock-файлом;
- не копировать конфигурацию из документации другой major-версии.

## 5. Архитектурные правила

Проект является одним приложением Next.js для Mini App, публичного браузерного просмотра, API, Telegram webhook и CRM.

Сохранять ясные границы:

- UI-компоненты не содержат серверных секретов и правил авторизации;
- Route Handlers и Server Actions являются транспортным слоем, а не местом для всей бизнес-логики;
- бизнес-правила размещать в сервисах `catalog`, `cart-pricing`, `ordering`, `telegram-auth`, `notifications`, `admin`, `settings`;
- Zod-схемы использовать на серверной границе;
- все операции с правами доступа проверять на сервере;
- не полагаться только на скрытые кнопки, layout, proxy или middleware;
- избегать дублирующего API, когда Server Action полностью покрывает административный сценарий;
- публичные данные можно кэшировать только с корректной инвалидацией;
- персональные данные, сессии и заказы никогда не помещать в публичный кэш;
- не хранить изменяемое состояние запроса в module scope.

Не добавлять в MVP отдельные микросервисы, Redis, постоянные background workers и платные обязательные зависимости.

## 6. Telegram Mini App

- Каталог и корзина должны работать в обычном браузере для QA.
- Checkout, профиль и заказы требуют проверенной Telegram-сессии.
- Передавать серверу сырой `initData`, а не отдельный `telegramId` как доказательство личности.
- На сервере проверять HMAC-подпись, использовать постоянное по времени сравнение и ограничивать возраст `auth_date`.
- `initDataUnsafe` разрешено использовать только для неподтверждённого отображения до серверной проверки; оно не является авторизацией.
- Telegram ID хранить без потери точности.
- Telegram Back Button, haptics, темы и viewport APIs применять только после feature detection.
- Учитывать `safeAreaInset`, `contentSafeAreaInset`, нижнюю навигацию и экранную клавиатуру.
- Любой dev-bypass должен быть невозможен в production.

## 7. Telegram-бот и webhook

- Не записывать `TELEGRAM_BOT_TOKEN` и webhook secret в код, fixtures, логи или репозиторий.
- Production использует только HTTPS webhook.
- Проверять `X-Telegram-Bot-Api-Secret-Token` до обработки update.
- Ограничивать тип и размер тела запроса.
- Дедуплицировать update по `update_id` с уникальным ограничением в БД.
- Отвечать Telegram быстро; не выполнять длительные ожидания внутри webhook.
- Не считать доставку сообщения гарантированной.
- Ошибка уведомления не должна откатывать созданный заказ.
- Записывать результат отправки в `NotificationLog`, санитизировать ошибку и предоставлять ограниченный ручной retry.
- Не запускать бесконечные автоматические повторы.
- Для serverless grammY заранее задавать информацию о боте, если это устраняет лишние `getMe` запросы.

## 8. Заказы и деньги

- Все суммы хранить и вычислять целым числом копеек; `float` для денег запрещён.
- Клиент не является источником истины для цены, скидки, доставки, итога и наличия.
- Непосредственно перед созданием заказа сервер повторно читает товары и настройки из БД.
- Заказ, позиции и начальную историю статуса создавать в одной транзакции.
- `OrderItem` хранит snapshot названия и цены.
- Каждый checkout использует idempotency key с уникальным ограничением.
- Повторный запрос с тем же ключом не создаёт новый заказ.
- Количество каждой позиции, число разных позиций и общий размер payload должны иметь пределы.
- Переходы статусов задаются явной таблицей допустимых переходов.
- Каждое изменение статуса записывается в историю с автором и временем.
- Публичные идентификаторы заказов должны быть непредсказуемыми или безопасными читаемыми номерами, которые нельзя использовать для обхода проверки владельца.

## 9. Режим приёма заказов

До подключения действующего ресторана использовать только:

```dotenv
ORDER_MODE=private_test
```

В `private_test`:

- каталог доступен для просмотра;
- checkout доступен только Telegram ID из серверного allowlist;
- публичному посетителю показывается «Приём заказов сейчас закрыт»;
- тестовый признак хранится внутри БД и CRM;
- тестовые заказы не учитываются как реальная выручка и не уходят реальным операторам или клиентам.

`ORDER_MODE=live` нельзя включить только кнопкой CRM. Сервер должен потребовать подтверждённую конфигурацию:

- хостинг, разрешающий коммерческое использование;
- действующий оператор;
- реальные зоны и условия доставки;
- доступные способы оплаты;
- достоверные контакты и правовые сведения;
- готовность исполнять реальные заказы.

## 10. Prisma и Neon

- Для Prisma 7 следовать `prisma-orm-setup` и его reference для PostgreSQL 7.
- Runtime использует pooled connection string.
- CLI/миграции используют direct connection string, если это требуется выбранной конфигурацией.
- `DATABASE_URL` и `DIRECT_URL` должны указывать на одну целевую БД/branch соответствующего окружения.
- Не печатать connection strings и секреты в вывод команд.
- Изменять схему только воспроизводимыми миграциями.
- Не выполнять `prisma migrate dev` в обработчике production-запроса или во время запуска приложения.
- Seed должен быть идемпотентным либо иметь ясно задокументированное повторное поведение.
- Seed не содержит реальных клиентов и персональных данных.
- Переиспользовать Prisma Client с корректным lifecycle для Next.js development/serverless.
- Проверять индексы для slug, `telegramId`, order number, idempotency key, `update_id`, статуса и частых admin-фильтров.
- Избегать N+1 запросов и не выбирать лишние персональные поля.
- Preview и production не должны случайно использовать одну изменяемую БД без осознанной настройки.

## 11. Административная авторизация

- Публичная регистрация запрещена.
- Первый администратор создаётся отдельной серверной командой из env.
- Пароль хранится только как Argon2id или другой актуальный адаптивный хеш.
- Использовать Secure, HttpOnly и подходящий SameSite для production cookies.
- Реализовать ограничение попыток входа.
- Не раскрывать, существует ли конкретный email, через разные сообщения об ошибке.
- Проверять сессию и роль во всех admin Route Handlers и Server Actions.
- Защита маршрута через `proxy.ts` служит ранним redirect, а не единственным контролем доступа.
- Учитывать CSRF для cookie-аутентифицированных мутаций согласно выбранной auth-библиотеке.
- Административные и приватные страницы помечать `noindex`.

## 12. Vercel Hobby

- Hobby применяется только для личного некоммерческого тестирования.
- Реальная коммерческая эксплуатация требует разрешающего тарифа или другого хостинга.
- Не обходить лимиты и условия провайдера.
- Не использовать локальную файловую систему Functions для постоянных uploads.
- Фото MVP хранить как подготовленные assets в `public/`.
- Не строить критические процессы на Cron; на Hobby он редкий и неточный.
- Не строить надёжность на `setTimeout`, незавершённых promises или памяти экземпляра функции.
- `after()`/`waitUntil()` допускаются только для короткой некритичной работы; факт необходимости уведомления должен находиться в БД.
- Сохранять небольшой payload, короткие Route Handlers и контролируемый function bundle.
- Выбирать регион Vercel близко к Neon.
- Перед размещением сверять текущие квоты Vercel и Neon по официальной документации.

## 13. Дизайн и frontend

- Основной язык интерфейса — русский, валюта — ₽.
- Приоритетные viewport: 320–430 px; также проверять 768, 1024 и 1440 px.
- Визуальный характер: современный японский food-бренд, премиальный, аппетитный и собранный.
- Базовое направление: глубокий угольный, тёплый молочный, томатно-красный акцент.
- Создать систему токенов; не использовать случайные цвета и один одинаковый radius для всех элементов.
- Типографика должна качественно поддерживать кириллицу.
- Один выразительный визуальный приём предпочтительнее множества украшений.
- Не использовать стереотипную японскую декорацию без функциональной или содержательной причины.
- Не использовать фиктивные отзывы, рейтинги, награды, скидки, счётчики заказов, адреса, телефоны, реквизиты и обещания ETA.
- Не показывать на клиентских страницах слова о портфолио, учебном или демонстрационном характере проекта.
- Loading, empty, error, retry и unavailable состояния обязательны.
- Touch targets, клавиатура, focus styles, alt-тексты, контраст и `prefers-reduced-motion` обязательны.
- Не добавлять неработающие кнопки, формы, фильтры, модификаторы и пустые страницы.

### Изображения

- Использовать реальные подходящие фотографии еды с разрешённым использованием.
- Не использовать фото одного блюда для разных несоответствующих товаров.
- Не использовать чужие логотипы и брендированные фотографии ресторанов.
- Хранить оптимизированные WebP/AVIF локально в `public/images/products`.
- Для каждого asset фиксировать источник, автора и основание использования в `ASSET_SOURCES.md`.
- Не использовать permanent hotlinking.
- Проверять отсутствие битых изображений и корректность alt-текстов.

## 14. React и производительность

- По умолчанию использовать Server Components; добавлять `"use client"` только на необходимой интерактивной границе.
- Не отправлять клиенту лишние поля и крупные объекты из Server Components.
- Параллелить независимые серверные запросы, избегать waterfall.
- Не создавать ненужные эффекты и производное состояние.
- Версионировать и минимизировать схему локальной корзины.
- Загружать изображения с известными размерами и подходящими responsive sizes.
- Не импортировать тяжёлые библиотеки в общий клиентский bundle.
- Не использовать barrel imports, если они ухудшают tree shaking.
- Для длинного каталога рассмотреть `content-visibility` или разумную пагинацию/виртуализацию после измерения.
- Не применять мемоизацию без измеримой причины.
- После значимых React-изменений сверяться с `vercel-react-best-practices`.

## 15. Работа с файлами и секретами

- Не фиксировать `.env`, токены, пароли, database URLs и реальные Telegram chat IDs.
- Поддерживать `.env.example` без настоящих значений.
- Не помещать секреты в переменные с префиксом `NEXT_PUBLIC_`.
- Не логировать raw `initData`, токены, полный телефон, полный адрес и пароль.
- Маскировать персональные данные в диагностике.
- Не изменять несвязанные пользовательские файлы.
- Не выполнять destructive Git-команды без явного запроса пользователя.
- Не переписывать миграции, уже применённые к общей БД; создавать новую миграцию.
- Новые зависимости добавлять только при реальной необходимости и после проверки поддержки.

## 16. Команды и проверки

После создания проекта поддерживать следующие scripts или их документированный эквивалент:

```text
npm run dev
npm run lint
npm run typecheck
npm run test
npm run test:e2e
npm run build
```

Минимум перед завершением реализации этапа:

- выполнить lint для затронутого кода;
- выполнить TypeScript typecheck;
- выполнить релевантные unit/integration тесты;
- выполнить production build при изменении маршрутов, конфигурации, Prisma или зависимостей;
- для UI выполнить реальную браузерную проверку, одного build недостаточно;
- для миграций выполнить безопасную проверку схемы и read-only запрос к целевой БД без вывода секретов.

Не заявлять, что тест прошёл, если команда не запускалась. Если проверка невозможна, назвать конкретную причину и оставшийся риск.

## 17. Browser и визуальный QA

При доступности Browser plugin применять его первым согласно `frontend-testing-debugging`. Если он отсутствует, использовать Playwright и зафиксировать причину fallback.

Для каждого существенного UI-изменения проверить:

- правильный URL и заголовок страницы;
- наличие содержательного интерфейса;
- отсутствие framework error overlay;
- отсутствие релевантных console errors;
- основной пользовательский переход и изменение состояния;
- мобильный и desktop viewport;
- отсутствие clipping, overlap, horizontal scroll и перекрытия safe area;
- скриншоты, подтверждающие визуальные выводы.

Скриншоты, traces и временные QA-скрипты не сохранять в репозиторий без отдельной необходимости.

## 18. Обязательные тестовые свойства

Реализация должна доказать как минимум следующее:

1. Каталог и изображения загружаются; поиск и фильтрация работают.
2. Корзина добавляет, удаляет, меняет количество и восстанавливается.
3. Денежные суммы рассчитываются без ошибок float.
4. Неверный, просроченный или подменённый Telegram `initData` отклоняется.
5. Без Telegram-сессии нельзя оформить заказ или прочитать чужой заказ.
6. Сервер игнорирует подменённые клиентские цены и пересчитывает заказ.
7. Один idempotency key создаёт один заказ.
